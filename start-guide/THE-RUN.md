# THE RUN — Evidence-Gated Delivery, on one page

> The Start Guide is a coach, not a certification: its guardrails are
> heuristic defaults applied by your own agent. It hardens the builder;
> it never certifies the app.

The kit is a folder of markdown. The method it carries has a name, so
that it can be argued with: **Evidence-Gated Delivery**. Four laws, and
everything in the ten gates follows from them.

## The four laws

1. **No box without evidence.** A checked box carries a file path, a
   command with its trimmed output, or a URL. "Done", "I believe so" and
   "the framework handles it" are not evidence. Evidence records location,
   never value: where a secret lives, never what it is.
2. **No gate without a human GO.** The agent plans, asks and holds the
   line; it never advances a gate on its own authority, never infers a GO
   from enthusiasm, and never drops the coin that starts the run. The
   human can overrule any gate — on the record, through a waiver, once.
3. **The record outranks memory.** An append-only journal, a scoreboard
   regenerated from it, a screen rendered from the scoreboard — and never
   the other way round. New session, new machine, new agent: the run
   resumes from the files, not from anyone's recollection.
4. **The builder is hardened; the app is never certified.** Belts, gates
   and the celebration speak about the person and the process. The one
   permitted sentence is "checked and evidenced, per the Start Guide's
   heuristics." Nothing here inspects, scans or vouches for an
   application.

## What it is not

- **Not a scanner.** The kit ships three git guards and one screen hook,
  and nothing else executes. The guards catch three specific mistakes;
  the rest of the run is judgment, written down, applied by your agent.
- **Not a certification.** A run with three waivers is still a completed
  run, and the record that says so is worth more than a clean-looking
  one that lies.
- **Not a spec method.** Spec-driven development answers "what are we
  building" before the code; the run answers "will it survive being
  shipped" while the code is built. The two are complementary — Spec Kit
  (https://github.com/github/spec-kit) is the method this kit cites for
  the first question, as inspiration and never as authority.
- **Not a scorecard.** Counts and ratios, never a percentage, never a
  derived score, never a streak. Momentum comes from facts about your
  own work, never from praise.

## Two paths, one method

- **The run** — ten gates, from 00-KICKOFF to 90-SHIP, for a project that
  will carry real users.
- **The five-gate path** — the SMALL RUN: five gates in full, four reduced
  to one box each, for a weekend build. Same evidence, same GO, same
  record. Smaller, not looser; one sentence ("full run") reopens
  everything.

## Where the method leaves you

At the end of a run you hold a journal a stranger can read, a scoreboard
you did not hand-edit, a run belt that says which questions you faced,
and a Ship Check you ran the week you shipped. You can say exactly what
you did. You still cannot say your app is secure — and now you know why
nobody honest can.

Works offline, forever: no network call, no telemetry, no account. Free,
under Apache-2.0, with the honesty line above required to travel with
every copy.
